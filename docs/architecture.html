The Cosmos SDK · architecture

How a game talks through The Cosmos

No game server and no Cosmos relay. Players reach each other directly over libp2p, fall back to Steam's relay when direct fails, and keep slow, lasting data (notes, graves, session listings) in a shared DHT.

The stack

One cosmos.dll per game. Fast traffic goes over a path; async data goes into the DHT.

real-time path, direct real-time path, Steam fallback async data

Joining with a code

The code is the only secret. The listing is locked with keys that come from the code and the current UTC day, so the people storing it can't read it, and a code-to-topic lookup table goes stale every day. The join secret and session key are random per session and travel inside the locked listing.

The DHT and the gossip mesh

Every record put goes out two ways at once. The Kademlia DHT stores it, so a player who arrives later can still look it up. The gossip mesh pushes it live to the players who are watching that topic right now, such as everyone on the same dungeon level when a note, grave or ghost appears, or everyone browsing the lobby list when a public run updates its listing.

Leaving a level drops the subscription, and the player leaves that topic's mesh. Session listings use the same put, but nobody subscribes to their opaque topics, so joiners find them by DHT lookup only.

stored, looked up later pushed live to subscribers
